# Telegram Shop Bot — Stability & Architecture 19

Production build: `STABILITY-ARCHITECTURE-19`

Эта сборка сохраняет текущий интерфейс магазина, Premium emoji, цвета кнопок, каталог и бизнес-логику, но переводит критические части на более устойчивую production-основу.

## Что добавлено

### 1. Бот больше не падает из-за временного недоступного Telegram API
При старте бот ждёт `api.telegram.org` и повторяет запросы с задержками. `setMyCommands` и `deleteWebhook` больше не завершают процесс при `TelegramNetworkError`, `WinError 121`, временном таймауте или FloodWait. Если polling неожиданно оборвётся, он запускается повторно. Общий таймаут HTTP-сессии задаётся через `TELEGRAM_REQUEST_TIMEOUT`.

### 2. FSM сохраняется после перезапуска
Aiogram теперь использует `SQLiteStorage` в `shop.db`, а не временный `MemoryStorage`. Оформление заказа, загрузка чека и админские пошаговые формы не теряют состояние после обычного рестарта процесса.

### 3. Транзакционное создание заказа и резерв товара
При создании заказа остаток резервируется атомарно на `RESERVATION_MINUTES` (по умолчанию 20 минут). Два покупателя не смогут одновременно успешно зарезервировать последнюю единицу товара.

При отправке ручного чека резерв продлевается на `RESERVATION_RECEIPT_HOURS` (по умолчанию 24 часа), чтобы товар не освободился во время проверки оплаты. Если первоначальный резерв уже истёк, бот сначала атомарно проверяет остаток заново и только затем принимает чек/воссоздаёт резерв.

Подтверждение оплаты теперь идемпотентно: повторное нажатие админом или повторный callback оплаты не списывает остаток и бонусы второй раз.

Покупательский каталог показывает **доступный** остаток уже за вычетом активных резервов. Админ не сможет удалить вариант/товар или уменьшить физический остаток ниже количества, которое уже удерживается активными заказами. После отклонения чека резерв сокращается обратно до обычного окна оплаты.

Подтверждение оплаты также защищено от повторных уведомлений: двойное нажатие не должно повторно отправлять покупателю одно и то же подтверждение.

### 4. SQLite production-настройки
Используются WAL, `busy_timeout=30000`, `synchronous=NORMAL` и индексы для заказов, клиентов, товаров, истории статусов и корзины. Это снижает вероятность `database is locked` и ускоряет растущую базу.

### 5. Автоматические проверенные backup
Перед startup-миграциями бот создаёт отдельную проверенную `pre_migration_*.db` копию существующей базы (хранятся последние 3). После запуска фоновый worker создаёт обычный backup каждые `BACKUP_INTERVAL_HOURS` (24 часа по умолчанию), проверяет копию через `PRAGMA quick_check` и хранит последние `BACKUP_KEEP` копий (14 по умолчанию).

Папка: `BACKUP_DIR=backups`.

### 6. Единый поиск в админке
На главной админ-панели появилась `🔎 Поиск по магазину`.

Можно ввести:
- номер заказа;
- Telegram ID;
- `@username`;
- телефон;
- ФИО;
- название/категорию товара.

Результаты сразу ведут в карточку заказа, клиента или товара.

### 7. Premium emoji — семантический поиск
Помимо обычного emoji теперь можно написать смысл, например:
- `доставка`;
- `оплата`;
- `магазин`;
- `удаление`;
- `настройки`;
- `успех`;
- `ошибка`;
- `поддержка`.

Бот покажет подходящие Premium emoji из всех импортированных паков.

### 8. Premium emoji — пресеты единого стиля
`Настройки → Premium emoji → 🎨 Пресеты стиля`:
- Minimal / Outline;
- macOS / iOS;
- Telegram UI.

Пресет пытается подобрать одинаковую визуальную семью для уже используемых emoji в текстах и кнопках. Он не отправляет покупателям никаких технических сообщений.

### 9. Более «приложенческая» админка
Основные листинги (товары, клиенты, бонусы, промокоды, поиск, диагностика) переиспользуют текущее bot-сообщение через edit вместо создания нового сообщения при каждом переходе, когда Telegram это позволяет.

### 10. Центральный error-handler
Необработанные ошибки получают короткий ID вида `A1B2C3D4`. Полный traceback пишется в лог, а пользователь получает безопасное короткое сообщение с ID. Старые молчаливые `except Exception: pass` в ключевых местах заменены логированием.

### 11. Полная диагностика
`Настройки → 🛠 Диагностика → 🩺 Полная проверка системы` проверяет:
- Telegram Bot API;
- SQLite quick_check и WAL;
- запись/чтение БД;
- свободное место;
- последний автоматический backup;
- аптайм процесса и количество активных резервов;
- Premium custom emoji через Telegram;
- доступность endpoint СДЭК (если настроен);
- доступность endpoint Почты России (если настроена).

Также можно создать проверенный backup вручную.

### 12. Секреты не входят в production ZIP
В архиве нет `.env`. Есть только `.env.example`. На сервере оставьте существующий `.env` или переменные окружения хостинга. `config.py` больше не перезаписывает уже заданные переменные окружения значениями из `.env`.

### 13. Архитектура и эксплуатация
Критическая инфраструктура вынесена из монолита в отдельные модули: `runtime_app.py`, `production_runtime.py`, `sqlite_fsm.py`, `workers.py`, `admin_search.py`, `premium_semantic.py`, `diagnostics.py`, `admin_sections.py`, `admin_auth.py`, `ui_render.py`, `logging_setup.py`. Это отделяет запуск, фоновые workers, FSM, диагностику, поиск и UI-инфраструктуру от бизнес-обработчиков.

FSM-обновления дополнительно изолируются по пользователю, а polling имеет ограничение одновременных задач, чтобы очередь апдейтов не раздувала память при всплеске нагрузки. Логи пишутся и в консоль, и в ротационный `logs/bot.log`.

### 14. Автотесты регрессий
В папке `tests/` есть проверки для:
- `⭐` / `⭐️` Unicode-нормализации;
- замены обычного emoji на Premium без дубля;
- удаления fallback emoji у Premium-кнопки;
- semantic emoji search;
- постоянного FSM;
- retry startup;
- отсутствия старого mass-push обновления меню;
- атомарного резерва/идемпотентных маркеров оплаты;
- безопасного повторного резерва после истечения старого hold;
- отсутствия молчаливых `except Exception: pass`;
- защиты складских остатков активными резервами;
- ограничения polling concurrency и FSM event isolation;
- валидности SQL production-индексов;
- синтаксиса Python-модулей.

Запуск:

```bash
python -m unittest discover -s tests
```

## Запуск

Рекомендуется Python 3.11+.

```bash
pip install -r requirements.txt
python bot.py
```

Dockerfile использует Python 3.11.

## Важное при обновлении

1. Сохраните рабочий `.env` / переменные окружения хостинга.
2. Замените файлы проекта новой сборкой.
3. `shop.db` можно оставить текущую — миграции создают таблицу резервов, FSM и новые колонки автоматически.
4. Выполните полный Rebuild/Deploy.
5. Откройте `/admin → ⚙️ Настройки → 🛠 Диагностика → 🩺 Полная проверка системы`.

## ADMIN-ORDER-UX-23

- После подтверждения оплаты заказ не переводит администратора в режим ввода трека. Он автоматически появляется в `Заказы → К отправке`.
- Основной рабочий процесс админа: `Проверить оплату → К отправке → добавить трек → Завершение`.
- Промежуточные ручные статусы сборки больше не нужны; старые заказы с такими статусами отображаются в `К отправке` для совместимости.
- Публичные номера заказов имеют вид `#DX12XX`: 6 случайных букв/цифр. Внутренний числовой ID остаётся только в базе и callback-данных.
- Старым заказам публичные коды назначаются автоматически при `init_db()`. Поиск админки понимает код с `#` и без него.
- Экспорт Excel показывает публичный номер заказа вместо внутреннего ID.
